# SOAP quirks

Короткий список практических особенностей Дребеденег, которые SDK учитывает или документирует.

## Endpoint

Официальный WSDL доступен по `/soap/dd.wsdl`, но внутри содержит `soap:address` на `http://www.drebedengi.ru/soap/`. SDK всегда задает `location` из `Endpoint`, чтобы работали `drebedengi.me` и кастомные домены. По умолчанию используется только `Endpoint::RU_BASE_URI`; зеркало ME или последовательность failover нужно указывать явно. `location` и `exceptions` зарезервированы транспортом и не могут быть переопределены через caller-provided `soapOptions`; остальные SOAP options сохраняются.

`ClientOptions` явно задаёт connect timeout 10 секунд, read timeout 30 секунд
и WSDL memory cache. Raw `soapOptions` имеют приоритет, чтобы сохранить
совместимость и escape hatch для нестандартного окружения.

## anyType

Большинство ответов описано как `anyType`, поэтому WSDL не является достаточным источником типов. SDK мапит реально используемые поля в DTO и оставляет исходный массив в `raw`.

## Деньги и точность валют

SOAP поле `sum` хранится как integer minor units. В старой документации это описано как сотые доли:

```text
-1234 => -12.34
```

Но Дребеденьги поддерживают криптовалюты с большей точностью. По данным публичной новости от 2025-07-29, всем криптовалютным операциям добавили больше знаков после запятой: по умолчанию 4, для дорогих валют 6 и более.

Практическое поле `getCurrencyList`:

```text
ratio=1       => 2 знака после запятой
ratio=1000000 => 8 знаков после запятой
```

SDK лениво загружает `getCurrencyList` и кэширует результат в экземпляре
`DrebedengiClient` до явного `refresh()` или типизированной mutation валют.
Поэтому суммы, полученные через `RecordService`, `BalanceService` и
`SyncService::initialRecords()`, сразу имеют правильный `scale` и связанный
`currencyId`. То же относится к вычисленному `Record::balanceAfter`. Для
initial sync каталог загружается до state-changing `getRecordList`, чтобы
ошибка справочника не возникла уже после очистки серверной дедупликации.

Для записи рекомендуемый конструктор — `$currency->amount('0.00001234')`. Старый
`MoneyAmount::fromDecimalString()` сохранён для совместимости, но перед `setRecordList` SDK
проверяет его scale по выбранной валюте. Если сумма была создана через `Currency::amount()`,
дополнительно проверяется совпадение связанного `currencyId` с аргументом операции. Ошибка
возникает до SOAP-вызова.

`MoneyAmount::fromFloat()` и старый `withScale()` объявлены устаревшими.
`rescale()` сохраняет десятичное значение и отклоняет потерю значащих цифр,
`reinterpretScale()` явно меняет смысл неизменных minor units. Все операции
проверяют диапазон PHP integer; `PHP_INT_MIN` форматируется без `abs()`.

Низкоуровневые `Record::fromSoap()` и `BalanceItem::fromSoap()` по-прежнему можно вызвать без
`Currency`; этот legacy-вариант оставляет scale `2`. Для currency-aware маппинга нужно передать
третьим/вторым аргументом соответствующий `Currency`, но обычному пользователю SDK это делать
не требуется.

## Остатки

`getBalance` принимает дату без времени и четыре независимых флага. `BalanceQuery` даёт им
прикладные имена:

```text
restDate       BalanceQuery::at(), дата форматируется в timezone аккаунта
is_with_accum  subtractAccumulations(), вычесть зарезервированные накопления
is_with_duty   subtractDebts(), вычесть долги
is_with_hidden includeHidden(), включить скрытые счета
is_with_null   includeZero(), включить счета с нулевым остатком
```

Без `BalanceQuery::at()` сервер возвращает остатки на текущую дату. Все флаги по умолчанию
выключены, как и в SOAP API.

## Фильтры операций

Для чтения операций в оригинальной валюте нужен `r_currency=0`. Значение `1` означает валюту с ID `1`, а не оригинальную валюту.

Рабочий detail-фильтр:

```php
[
    'is_report' => true,
    'is_show_duty' => true,
    'r_period' => 0,
    'period_from' => '2026-01-01',
    'period_to' => '2026-01-31',
    'r_how' => 1,
    'r_what' => 6,
    'r_currency' => 0,
    'r_is_place' => 1,
    'r_place' => ['PLACE_ID'],
    'r_is_tag' => 0,
    'r_is_category' => 0,
]
```

`is_report=true` вместе с `r_how=1` возвращает детальный журнал без server-side побочного
эффекта. Название legacy-параметра вводит в заблуждение: `true` не означает обязательную
агрегацию, она включается только через `r_how=2` или `r_how=3`.

`RecordQuery` покрывает все периоды detail-журнала: произвольный диапазон, сегодня, текущий
и прошлый месяц, текущий квартал, текущий и прошлый год, всё время и последние 20 операций.
Пустой `RecordQuery` означает последние 20 операций, как и `RecordService::list()` без query.
`relative_date` задаётся через `relativeTo()` и форматируется в timezone аккаунта. Также доступны
`r_who`, `is_show_duty`, `is_with_planned` и направления include/exclude для счетов, тегов и
категорий. Агрегирующие `r_how=2/3` намеренно не входят в `RecordQuery`, потому что сервер
возвращает для них строки отчёта другой формы, а не `Record`.

Detail-журнал SDK допускает только `r_currency=0`: при пересчёте сервер может вернуть дробный
`difference`, который не является обновляемой операцией с целым количеством minor units.
Пересчёт валют поддерживается типизированным `ReportQuery::convertedToCurrency()`.

Плановые строки detail-журнала помечены `is_planned` и дополнительно содержат `repeat_id`,
`period_id` и `init_date`; SDK отображает их в типизированные поля `Record`. Сочетание
`includePlanned()` с `withBalanceAfter()` отклоняется до SOAP-вызова: фактический `getBalance`
не является достаточным основанием для однозначного прогнозного остатка.

## Агрегированные отчёты

В report-mode сервер поддерживает две отдельные формы результата:

```text
r_what=3, r_how=3  расходы по категориям
r_what=2, r_how=2  доходы по источникам
```

Обе формы возвращают дерево с `budget_object_id`, `parent_id`, `name`, `nochild`, `currency_id`
и `difference`. Поэтому SDK отображает их в `ReportRow`, а не в `Record`. `r_middle` принимает
`0`, `86400`, `604800` или `2592000` для отсутствия усреднения либо среднего за день, неделю
или месяц.

При `r_currency=0` `difference` обычно является целым числом minor units. После пересчёта в
выбранную валюту сервер может вернуть дробное значение, например `-9057.3831561769` minor units.
`DecimalMoneyAmount` хранит такое значение строкой и не округляет его до integer или float.

`is_report=false` предназначен сервером для первоначальной синхронизации. После подготовки
ответа сервер очищает `budget_sync_last` для текущих пользователя и API ID — служебные
соответствия `client_id` / `server_id`, используемые для защиты повторной записи после
потерянного ответа. Поэтому обычный `RecordService::list()` использует `true`, а legacy-режим
доступен только через явно названный `SyncService::initialRecords()`.

Та же таблица используется для дедупликации `client_id` при `setRecordList`,
но сервер после каждого успешного вызова удаляет старые соответствия этого
типа и сохраняет только вставки текущей пачки. Поэтому `RecordWriteToken`
пригоден для немедленного повтора того же запроса, но не является долговечным
idempotency key. Токен сохраняет только ID: дата, суммы, комментарий и остальные
аргументы тоже должны совпадать. При failover нельзя повторять запрос на прежнем
failover-клиенте; нужен отдельный клиент, закреплённый за endpoint из
`AmbiguousMutationException`, либо сверка результата чтением.

Типизированные поля `Record` одинаковы в обоих режимах. Поле `raw` намеренно сохраняет именно
серверный ответ, поэтому при обычном чтении в нём используются report-имена
`budget_account_id`, `difference` и `id2` вместо sync-имён `place_id`, `sum` и отдельных ID
связанных перемещения или обмена.

## Типы операций

```text
2 доход
3 расход
4 перемещение
5 обмен валют
6 все типы, только для фильтров
```

Для перемещения SOAP хранит две связанные записи с `server_move_id` или `client_move_id`.

Для обмена валют SOAP хранит две связанные записи с `server_change_id` или `client_change_id`.

Сервер отклоняет обмены, где обе стороны используют один и тот же `currency_id`.

## Timezone

SOAP API не отдает timezone аккаунта. Проверенные аккаунтные методы (`getUserIdByLogin`, `getRightAccess`, `getSubscriptionStatus`, `getExpireDate`, `getAccessStatus`) не содержат timezone.

`operation_date` передается как наивное значение `YYYY-MM-DD HH:mm:ss`. SDK интерпретирует входящие даты и форматирует исходящие даты в timezone из `ClientOptions`. Если timezone не задана, используется `date_default_timezone_get()`.

## Дерево мест хранения

`getPlaceList` возвращает и реальные счета, и строки-папки:

```text
type=4 реальный счет, можно использовать в операциях
type=9 папка/группа, нужна только для отображения дерева
```

Отрицательные `parent_id` — системные группы, а не обычные родительские объекты. Проверенный пример:

```text
parent_id=-3 группа "Скрытые суммы": счета видимы и принимают операции, но их баланс показывается отдельно и исключается из UI-итога
```

## Запись финансовых справочников

`setCategoryList`, `setSourceList` и `setPlaceList` используют одну внутреннюю
реализацию и требуют полный DAO payload даже для простого объекта. Проверенный
минимальный payload категории:

```php
[
    'client_id' => 123,
    'name' => 'Кафе',
    'parent_id' => '-1',
    'type' => 3,
    'is_hidden' => false,
    'is_for_duty' => false,
    'sort' => '0',
]
```

Для источника используется тот же набор с `type=2`. Для обычного счёта
`setPlaceList` дополнительно требует `type=4`, `purse_of_nuid`, `icon_id`,
`is_autohide`, `description` и `is_credit_card`. SDK намеренно предоставляет
`createAccount()`, но не обещает создание папок или server-managed счетов.

Имена категорий, источников и счетов ограничены 128 Unicode-символами, тегов —
64, валют и их code — 16. Все поля с префиксом `is_` сервер принимает только как
настоящий boolean.

Каждый `get*List` принимает `idList`. SDK проверяет положительные ID и удаляет
повторы до SOAP. Для категорий, источников и счетов это также обязательный
предохранитель перед удалением: `deleteObject(..., 'object')` не кодирует
конкретный тип справочника.

Все типизированные update/delete, а также `currencies()->setDefault()`, сначала
требуют полный доступ к аккаунту. Limited access маскирует часть состояния,
необходимого для безопасного read-modify-write и проверки объекта перед
удалением.

Удаление категории через `deleteObject(..., 'object')` зависит от связей:

- категория, использованная в операции, не удаляется до удаления этой операции;
- родительская категория с подкатегориями удаляется успешно, сервер удаляет всё поддерево.

Source хранится в том же иерархическом `budget_object` и удаляется через тот же
generic object path. SDK намеренно не добавляет leaf-only guard для категорий и
источников: перед удалением родителя вызывающий код должен проверить `tree()`,
если каскад не задуман.

Все типизированные update-методы затем загружают объект по ID и сохраняют
обязательные поля, которых нет в patch. Неизвестные ключи отклоняются, а
`server_id` всегда берётся из аргумента метода. Server-managed поля полного
legacy payload принимаются для совместимости, но игнорируются. Обычный patch
требует настоящий PHP `bool`; только полный legacy raw payload категории или
счёта может сохранить точные SOAP-токены `t/f/1/0`.

Сервер применяет HTML-экранирование к `name` и `description` при чтении. Для
read-modify-write SDK снимает ровно один этот слой; новый, явно отличающийся
текст пользователя не декодируется.

Legacy-реализация `setPlaceList` принудительно сбрасывает `is_credit_card` при
записи. SDK поэтому не обновляет credit-card счета, системные `is_for_duty`
счета, а также не отправляет через этот путь папки: вместо потенциальной потери
состояния выбрасывается `InvalidArgumentException`. Эти инварианты сверены с
[официальным SOAP-патчем Дребеденег](https://www.drebedengi.ru/?module=v2_aboutServer).

Удаление счёта на legacy-сервере неатомарно: сначала удаляется строка начального
остатка, затем сервер пытается удалить сам `budget_object`, без транзакции. SDK
поэтому разрешает `places()->delete()` только для обычного счёта без
`is_for_duty`, credit-card, purse owner и auto-hide состояния. Перед mutation
он выполняет безопасный `getRecordList` с `is_report=true`, периодом «всё
время», включёнными плановыми строками и фильтром по одному счёту. Найденная
операция блокирует удаление. Между preflight и `deleteObject()` остаётся
неустранимый server-side race с параллельной записью.

`setTagList` сам добавляет `family_id` и `user_id`, но требует name,
`parent_id`, `is_hidden`, `is_family` и `sort`. `getTagList` при этом может
вернуть теги других участников семьи. Типизированные update/delete сравнивают
`user_id` тега с `getUserIdByLogin` и отклоняют чужой или неизвестный owner:
иначе update переписал бы владельца на текущего пользователя, а delete удалил бы
чужой видимый семейный тег. При удалении тега сервер может удалить первое
`[TagName]` из комментариев связанных операций; один проход ограничен 1000
строками.

`setCurrencyList` имеет особенно опасную семантику: на каждом write сервер
принудительно ставит `ratio=1` и `is_investing=false`. SDK поэтому не обновляет
и не назначает default для currency с другим ratio или investing-state.
Создаваемая валюта по умолчанию hidden и non-default. Назначение нового default
возвращает в ответе строки прежней и новой default-валюты. Поэтому SDK никогда
не полагается на позицию строки: create сопоставляет ID по `client_id`, а
update/default подтверждают целевой `server_id`.

Непосредственно перед типизированным currency write SDK инвалидирует общий
каталог. Это важно даже до подтверждения ответа: mutation могла пройти, хотя
response потерян или не содержит ожидаемый ID. После успешного ответа каталог
перечитывается; после неоднозначного/некорректного следующий доступ снова
вызывает `getCurrencyList`. Обычный явный `refresh()` без предшествующей
mutation, наоборот, сохраняет последний валидный снимок при ошибке.

Сервер хранит client/server-сопоставления только последнего успешного write
каждого типа справочника для данного API ID. `ReferenceWriteToken` пригоден для
немедленного повтора точного payload, но следующий write того же типа заменяет
это окно дедупликации.

# Остаток после операции

Веб-отчёт Дребеденег принимает параметр `is_with_rest` и отображает остаток в каждой строке,
но SOAP `getRecordList` отклоняет этот параметр с ошибкой `parameter 'is_with_rest' not allowed`.
Обычный SOAP-ответ также не содержит рассчитанного остатка.

Поэтому `RecordQuery::withBalanceAfter()` не передаёт веб-параметр в SOAP. SDK получает остатки
на конец диапазона через `getBalance` и проходит все операции диапазона в обратном порядке.
Для отфильтрованных запросов нужен дополнительный нефильтрованный `getRecordList`, иначе остаток
нельзя корректно восстановить. Пересчитанная `r_currency` не поддерживается.
